# Java 21 가상 스레드 개발 연구 계획

## 1. 문서 목적

이 문서는 Java 21 가상 스레드 실험 구현 전에 개념 학습, 적용 이유, 실험 계획을 정리하기 위해 작성하였다.

본 프로젝트는 가상 스레드를 단순 실행 예제로 사용하는 것이 아니라, JDBC/MySQL 주문 처리 과정에서 발생할 수 있는 I/O 대기 구간과 연결하여 이해하는 것을 목표로 한다.

따라서 구현 전에 플랫폼 스레드와 가상 스레드의 차이, I/O 중심 백엔드 작업에서 가상 스레드가 의미 있는 이유, 실행 로그를 어떤 방식으로 남길지 먼저 정리한다.

## 2. 연구 배경

본 프로젝트의 기본 요구사항은 DB 설계, DAO/DTO 설계, JDBC 기반 CRUD, MySQL 연동이다.

하지만 이후 과정에서는 Spring 기반 AI 에이전트 서버, 실시간 응답, 비동기 AI 서빙, RAG 파이프라인, 클라우드 배포 같은 백엔드 확장 주제를 계속 다루게 된다.

이런 서버 작업에서는 DB 조회, 외부 API 호출, AI 서버 응답 대기처럼 CPU 계산보다 기다리는 시간이 긴 I/O 작업이 자주 발생한다.

Java 21의 가상 스레드는 이런 I/O 중심 작업을 더 가볍게 다루기 위한 현대 Java의 중요한 기능이다.

따라서 이번 프로젝트에서는 단순히 CRUD를 구현하는 데서 끝내지 않고, 주문 처리 작업을 가상 스레드로 실행해 I/O 대기 흐름을 관찰하는 실험을 포함한다.

| 학습 항목 | 학습 내용 | 확인 기준 |
| --- | --- | --- |

## 4. Stack/Heap 비유를 통한 이해

수업에서 배운 Stack과 Heap 개념은 가상 스레드를 이해할 때도 도움이 된다.

Stack은 지금 실행 중인 메소드, 지역 변수, 실행 흐름을 담는 작업 공간으로 이해할 수 있다.

Heap은 `new`로 생성된 객체처럼 여러 곳에서 참조되는 데이터를 보관하는 공간으로 이해할 수 있다.

요리 비유로 설명하면 다음과 같다.

| Java 개념 | 요리 비유 | 설명 |
| --- | --- | --- |
| Stack | 지금 요리 중인 작업대 | 현재 실행 중인 메소드와 지역 변수가 올라와 있는 공간 |
| Heap | 음식 창고 | 객체와 데이터가 저장되는 공간 |
| Platform Thread | 작업대를 계속 차지하는 요리사 | DB 응답을 기다리는 동안에도 작업 흐름이 묶일 수 있음 |
| Virtual Thread | 주문표 | 많은 작업을 가볍게 만들고 관리할 수 있음 |
| Carrier Thread | 실제 작업대를 쓰는 실행 스레드 | JVM 스케줄러가 가상 스레드를 올려 실행하는 실제 스레드 |

가상 스레드는 재료를 기다리는 주문의 상태를 잠시 보관해두고, 작업대에 해당하는 실행 스레드는 다음 주문을 처리하는 데 사용할 수 있는 방식으로 이해할 수 있다.

단, 이 비유는 이해를 돕기 위한 설명이며, 실제 JVM 내부 동작을 완전히 그대로 표현한 것은 아니다.

## 5. 프로젝트 적용 이유

본 프로젝트는 JDBC와 MySQL을 사용한다.

DB 조회나 저장 작업은 CPU 계산보다 DB 응답을 기다리는 시간이 발생할 수 있다.

이런 I/O 대기 작업이 여러 개 동시에 발생한다고 가정하면, 가상 스레드가 어떤 흐름으로 작업을 처리하는지 확인해볼 수 있다.

따라서 본 프로젝트에서는 여러 주문 처리 작업을 만들고, 각 작업을 Virtual Thread로 실행한 뒤, 콘솔 로그와 DB 로그를 통해 다음 정보를 확인한다.

| 기록 항목 | 의미 |
| --- | --- |
| 스레드 이름 | 어떤 스레드가 작업을 실행했는지 확인 |
| 작업 시작 시점 | 주문 처리 작업이 시작된 시간 |
| 대기 시작 시점 | DB I/O 대기 구간이 시작된 시간 |
| 대기 종료 시점 | DB I/O 대기 구간이 끝난 시간 |
| 작업 종료 시점 | 주문 처리 작업이 끝난 시간 |
| 전체 실행 시간 | 작업 시작부터 종료까지 걸린 시간 |
| 결과 상태 | 성공 또는 실패 여부 |

## 6. 실험 설계

가상 스레드 실험은 다음 흐름으로 설계한다.

```text
여러 주문 처리 작업 생성
-> 각 작업을 Virtual Thread로 실행
-> 작업 시작 로그 기록
-> DB 저장 또는 조회 작업 수행
-> I/O 대기 구간 기록
-> 작업 종료 로그 기록
-> VIRTUAL_THREAD_LOG 테이블에 실행 결과 저장
```

실험에서는 주문 처리 작업을 한두 개만 실행하지 않고, 여러 개의 작업을 자동으로 실행한다.

이를 통해 많은 I/O 대기 작업이 동시에 발생하는 상황을 단순하게 재현한다.

## 7. VIRTUAL_THREAD_LOG 설계 의미

`VIRTUAL_THREAD_LOG`는 단순히 스레드 이름만 저장하는 로그 테이블이 아니다.

이 테이블은 가상 스레드가 I/O 대기 구간을 어떻게 지나갔는지 확인하기 위한 실행 추적 로그이다.

`VIRTUAL_THREAD_LOG`는 `CAFE_ORDER`와 FK로 연결된다.

그 이유는 본 프로젝트의 실험 단위가 단순 스레드 실행이 아니라 주문 처리 작업이기 때문이다.

즉 로그를 통해 다음 질문에 답할 수 있어야 한다.

```text
이 로그는 어떤 주문 처리 작업에서 발생했는가?
해당 주문 처리 작업은 언제 시작되었는가?
DB I/O 대기는 언제 시작되고 언제 끝났는가?
전체 작업 시간은 얼마나 걸렸는가?
```

## 8. QA 확인 기준

QA Tester 관점에서는 단순히 코드가 실행되는지만 확인하지 않는다.

가상 스레드 실험 결과가 실제로 관찰 가능한지도 확인한다.

| 확인 항목 | 확인 방법 | 완료 기준 |
| --- | --- | --- |
| 여러 작업 실행 | 콘솔 로그 확인 | 여러 주문 처리 작업 번호가 출력됨 |
| 가상 스레드 사용 | `Thread.currentThread().isVirtual()` 확인 | `true` 값 확인 |
| 시작/대기/종료 기록 | 콘솔 로그와 DB 로그 확인 | 각 시점이 로그에 남음 |
| DB 저장 확인 | `virtual_thread_log` 조회 | 실행 추적 로그가 DB에 저장됨 |
| 실패 기록 확인 | 예외 발생 시 로그 확인 | 실패 상태와 메시지가 기록됨 |

## 9. 실험 범위와 한계

이 실험은 정밀한 성능 벤치마크가 아니다.

목표는 가상 스레드가 무조건 빠르다는 것을 증명하는 것이 아니라, I/O 중심 백엔드 작업에서 가상 스레드의 실행 흐름을 이해하는 것이다.

또한 DB 연결 수, MySQL 설정, PC 성능에 따라 실행 결과는 달라질 수 있다.

따라서 발표에서는 성능 수치보다 다음 내용을 중심으로 설명한다.

```text
여러 주문 처리 작업을 동시에 실행했다.
각 작업을 가상 스레드로 실행했다.
I/O 대기 구간을 콘솔과 DB 로그로 기록했다.
VIRTUAL_THREAD_LOG를 통해 실행 흐름을 확인했다.
```

## 11. 발표용 정리

저는 가상 스레드를 성능 튜닝 기술로 깊게 다루기보다는, Java 21 백엔드에서 I/O 중심 작업을 어떻게 더 가볍게 처리할 수 있는지 이해하는 데 초점을 두었다.

본 프로젝트에서는 JDBC/MySQL 주문 처리 과정에서 발생할 수 있는 DB I/O 대기 구간을 가상 스레드 실험과 연결하였다.

여러 주문 처리 작업을 Virtual Thread로 실행하고, 각 작업의 시작 시점, 대기 시작 시점, 대기 종료 시점, 종료 시점을 기록하여 실행 흐름을 확인할 예정이다.

특히 `VIRTUAL_THREAD_LOG` 테이블을 사용해 콘솔 로그뿐 아니라 DB에도 실행 추적 결과를 남기도록 설계하였다.
