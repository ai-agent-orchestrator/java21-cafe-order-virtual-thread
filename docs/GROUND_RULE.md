# Ground Rule

본 프로젝트의 1차 목표는 9월 과정 통과이다.

하지만 단순히 결과물을 제출하는 것이 아니라, 직접 설명할 수 있는 수준으로 핵심 개념을 이해하고 구현하는 것을 원칙으로 한다.

## 1. 프로젝트 목표

본 프로젝트는 기존 `cafe management system`을 기반으로 JDBC/MySQL 데이터 연동을 적용하고, Java 21 가상 스레드를 활용한 I/O 중심 작업 처리 흐름을 실험한다.

새로운 업무 기능을 많이 추가하는 것보다 기존 Java CRUD 구조를 복습하고, Java 21 백엔드에서 데이터 연동과 동시성 처리의 기초를 이해하는 데 집중한다.

## 2. 이해 중심 개발 원칙

- 이해하지 못한 코드는 그대로 제출하지 않는다.
- AI의 도움을 받되, 생성된 코드와 문서는 직접 읽고 실행해본 후 프로젝트에 반영한다.
- 설명할 수 없는 복잡한 기능은 과감히 제외한다.
- 많은 기능보다 핵심 요구사항을 정확히 구현하는 것을 우선한다.
- 발표에서 코드 흐름, DB 구조, Java 21 선택 이유를 직접 설명할 수 있어야 한다.

## 3. 범위 제한 원칙

- 웹 프론트엔드는 구현하지 않는다.
- 회원 등급, 쿠폰, 프로모션, 결제 상세, 복잡한 통계 기능은 제외한다.
- 새로운 CRUD를 처음부터 대량 개발하지 않는다.
- 기존 카페 주문 관리 시스템을 기반으로 DB 연동 구조를 확장한다.
- 추가 코딩은 Java 21 가상 스레드 이해와 실험에 직접 연결되는 부분에 집중한다.

## 4. Java 21 집중 원칙

- 본 프로젝트의 기술적 중심은 Java 21이다.
- Java 21을 선택한 이유를 설명할 수 있어야 한다.
- 가상 스레드가 무엇인지, 플랫폼 스레드와 어떻게 다른지 설명할 수 있어야 한다.
- DB I/O나 외부 API 호출처럼 대기 시간이 많은 작업에서 가상 스레드가 왜 의미 있는지 설명할 수 있어야 한다.
- 가상 스레드는 작은 실험 코드로 직접 구현하고 실행 결과를 확인한다.

## 5. AI 협업 원칙

AI는 단순 결과물 생성 도구가 아니라 요구사항 정리, 설계 초안 작성, 코드 검토, 문서 보완을 빠르게 반복하기 위한 협업 도구로 활용한다.

최종 방향과 반영 여부는 직접 판단하며, 이해하지 못한 코드나 설명은 프로젝트에 포함하지 않는다.

## 6. 기록 및 산출물 관리 원칙

본 프로젝트는 결과물뿐 아니라 의사결정 과정과 변경 이력을 함께 산출물로 관리한다.

따라서 ERD 설계 의사결정 과정, FK 설계 논리, GitHub Flow, 커밋 메시지, Pull Request 기록을 남겨 프로젝트의 진행 흐름과 기술 선택 이유를 추적할 수 있도록 구성한다.

기록 대상은 다음과 같다.

```text
- Ground Rule
- R&R + Daily Schedule + To-Do
- Branch Strategy
- Git/GitHub Requirement Checklist
- ERD Design Decision
- ERD FK Design
- Java 21 Virtual Thread Concept
- README
- Pull Request 기록
```

## 7. 최종 원칙

```text
기존 카페 주문 CRUD는 재사용한다.
업무 기능은 과하게 늘리지 않는다.
DB 연동 요구사항은 JDBC/MySQL로 충족한다.
Java 21 가상 스레드 실험은 실행 추적 로그로 기록한다.
내가 직접 설명할 수 있는 구조로 유지한다.
```
