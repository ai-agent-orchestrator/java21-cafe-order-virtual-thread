# ERD 설계 조건 초안 및 의사결정 과정

본 문서는 ERD 설계 조건 초안과 최종 ERD 도출 과정을 기록한다.

본 프로젝트는 1인 프로젝트이지만, ERD를 바로 작성하지 않고 실제 팀 프로젝트의 설계 회의처럼 여러 조건을 검토한 뒤 최종 구조를 결정했다.

타 팀은 여러 팀원이 의견을 나누며 엔티티를 확장하고 조정할 수 있지만, 본 프로젝트는 1인이 기획, 설계, 구현, 검증, 문서화를 모두 수행해야 한다.

따라서 ERD 설계 과정에서는 프로젝트 인원, 구현 가능 범위, 기존 코드 재사용 여부, 수업 요구사항, Java 21 가상 스레드 학습 목표를 함께 고려했다.

## 1단계. 프로젝트 목표와 현실 조건 확인

먼저 ERD 설계 전에 프로젝트의 목표와 현실 조건을 정리했다.

| 항목 | 내용 |
| --- | --- |
| 프로젝트 형태 | 1인 프로젝트 |
| 비교 조건 | 타 팀은 5인 내외 팀 프로젝트 |
| 개발 기반 | 기존 `cafe management system` 활용 |
| 1차 목표 | 9월 과정 통과 |
| 학습 목표 | Java 21 가상 스레드 이해와 실험 구현 |
| 구현 전략 | 새 기능 대량 개발보다 기존 구조 복습과 확장 |

이 단계에서 ERD는 복잡한 업무 기능을 모두 담는 것이 아니라, 기존 카페 주문 CRUD를 MySQL로 연동하고 Java 21 가상 스레드 실험을 기록할 수 있는 구조를 목표로 잡았다.

## 2단계. 기존 카페 주문 시스템 구조 분석

기존 프로젝트에는 이미 카페 주문 CRUD 흐름이 구현되어 있다.

```text
CafeOrderApplication
-> CafeOrderController
-> OrderService
-> OrderRepository
-> CafeOrder / OrderItem / CafeMenu
```

기존 구조에서 핵심 데이터는 다음 세 가지이다.

| 기존 Java 객체 | 의미 | ERD 후보 |
| --- | --- | --- |
| `CafeMenu` | 카페 메뉴 | `MENU` |
| `CafeOrder` | 주문 기본 정보 | `CAFE_ORDER` |
| `OrderItem` | 주문에 포함된 메뉴와 수량 | `ORDER_ITEM` |

따라서 기본 ERD는 기존 Java 객체와 자연스럽게 연결되도록 설계한다.

## 3단계. 확장 후보 검토

다른 팀의 ERD처럼 회원, 등급, 쿠폰, 프로모션, 결제, 통계 기능을 추가하는 방향도 검토할 수 있었다.

하지만 본 프로젝트의 핵심은 복잡한 쇼핑몰성 업무 기능이 아니라 Java 21 기반 백엔드 이해이다.

검토한 확장 후보는 다음과 같다.

| 확장 후보 | 채택 여부 | 판단 이유 |
| --- | --- | --- |
| 회원/회원등급 | 제외 | 기존 카페 주문 CRUD의 핵심 흐름이 아님 |
| 쿠폰/프로모션 | 제외 | 구현량이 커지고 Java 21 학습 초점이 흐려짐 |
| 결제 상세 | 제외 | 주문 등록 흐름만으로 CRUD 요구사항 충족 가능 |
| 복잡한 매출 통계 | 제외 | 발표와 구현 부담 증가 |
| 가상 스레드 실행 로그 | 채택 | 프로젝트의 핵심 목표인 Java 21 실험과 직접 연결 |

이 단계에서 업무 기능 확장은 최소화하고, 코딩을 추가한다면 Java 21 가상 스레드 실험과 직접 연결되는 부분에만 집중하기로 결정했다.

## 4단계. Java 21 가상 스레드 실험 반영

본 프로젝트는 Java 21을 기술적 중심으로 둔다.

특히 여러 주문 처리 작업을 Virtual Thread로 실행하고, 각 작업이 I/O 대기 구간을 어떤 흐름으로 지나가는지 확인하는 것을 목표로 한다.

따라서 단순 주문 CRUD 테이블만으로 끝내지 않고 `VIRTUAL_THREAD_LOG` 엔티티를 추가하기로 결정했다.

`VIRTUAL_THREAD_LOG`는 단순히 스레드 이름만 저장하는 로그가 아니라, 가상 스레드가 I/O 대기 구간을 어떻게 지나갔는지 확인할 수 있는 실행 추적 로그로 설계한다.

기록 대상은 다음과 같다.

```text
- 실험 이름
- 작업 이름
- 스레드 타입
- 스레드 이름
- 작업 시작 시점
- DB I/O 대기 시작 시점
- DB I/O 대기 종료 시점
- 작업 종료 시점
- 대기 시간
- 전체 실행 시간
- 실행 결과
```

이 설계를 통해 가상 스레드 실험이 단순 콘솔 출력으로 끝나지 않고, DB에 기록 가능한 결과물로 남도록 한다.

## 5단계. 최종 엔티티 선정

검토 결과 최종 ERD는 다음 네 개의 엔티티로 결정했다.

| 엔티티 | 역할 |
| --- | --- |
| `MENU` | 카페 메뉴 정보 저장 |
| `CAFE_ORDER` | 주문 기본 정보 저장 |
| `ORDER_ITEM` | 주문에 포함된 메뉴와 수량 저장 |
| `VIRTUAL_THREAD_LOG` | Java 21 가상 스레드 실험 실행 흐름 기록 |

최종 관계는 다음과 같다.

```text
CAFE_ORDER 1 : N ORDER_ITEM
MENU 1 : N ORDER_ITEM
CAFE_ORDER 1 : N VIRTUAL_THREAD_LOG
```

이 구조는 기존 카페 주문 CRUD를 유지하면서도, Java 21 가상 스레드 실험을 ERD에 명확히 반영한다.

## 6단계. 최종 ERD 설계 원칙 정리

최종 ERD 설계 원칙은 다음과 같다.

```text
1. 기존 cafe management system을 재사용한다.
2. 새로운 업무 기능을 과하게 추가하지 않는다.
3. 주문 CRUD 요구사항은 MENU, CAFE_ORDER, ORDER_ITEM으로 충족한다.
4. Java 21 가상 스레드 실험은 VIRTUAL_THREAD_LOG로 기록한다.
5. 추가 코딩은 가상 스레드 이해와 실험에 직접 연결되는 부분에 집중한다.
6. 내가 직접 설명할 수 있는 구조로 유지한다.
```

따라서 본 프로젝트의 ERD는 복잡한 업무 확장형 ERD가 아니라, 기존 카페 주문 관리 시스템의 DB 연동과 Java 21 가상 스레드 실행 추적을 위한 목적형 ERD이다.

## 최종 요약

본 ERD는 1인 프로젝트라는 현실적 조건을 고려하여 복잡한 업무 기능 확장을 줄이고, 기존 카페 주문 CRUD를 MySQL로 연동하는 최소 구조를 기반으로 설계했다.

동시에 프로젝트의 핵심 목표인 Java 21 가상 스레드 이해와 실험 구현을 반영하기 위해 `VIRTUAL_THREAD_LOG` 엔티티를 추가했다.

이를 통해 여러 주문 처리 작업이 Virtual Thread로 실행될 때 I/O 대기 구간을 어떤 흐름으로 지나가는지 기록하고 설명할 수 있도록 했다.
